# Mode B Claude-only Policy (v5.6.0) — Design Spec

**Date:** 2026-05-07
**Mode:** A (Solo, lightweight scope)
**Branch:** `feature/v5.6.0-mode-b-policy-2026-05-07`
**Strategy:** α (Runtime enforcement) — chosen over β (Content differentiation) per analysis

---

## 1. Problem

Mode B (Team Spine) workflow requires Claude-specific Task tool capabilities:
- Subagent dispatch with `subagent_type` + `model` + `isolation` parameters
- Per-task model override using Claude model names (`haiku`/`sonnet`/`opus`)
- Worktree-isolated parallel execution

These capabilities differ across harnesses. Running Mode B on Cursor/Codex/OpenCode causes partial failures: subagent dispatch may not honor `model` parameter; phase agents may not be discoverable in the same way.

v5.5.1 fixed plugin path detection so Mode A works cross-platform. v5.6.0 closes the gap by formalizing Mode B as Claude-only and adding runtime enforcement at the Mode Selection Gate.

## 2. Goal

Mode Selection Gate auto-forces Mode A when active harness is not Claude Code. User can override (per existing user-decision-wins rule) but with explicit warning.

## 3. Non-goals

- Do **not** ship per-marketplace bundles (Strategy β rejected — over-engineering for project size)
- Do **not** abstract away Mode B internals to make them cross-platform (deferred indefinitely; out of scope)
- Do **not** remove phase agent files from non-Claude installs (additive policy only)
- Do **not** break v5.5.x backward compat

## 4. Strategy α — Runtime Enforcement

Single codebase, single release. Mode Gate enforces policy at workflow time. Detection via:
1. Environment variable check (e.g., `$env:CLAUDECODE`, `$env:CURSOR_*`, `$env:CODEX_*`, `$env:OPENCODE_*`)
2. `.planning/config.json` `active_harness` field (explicit user override, default `auto`)
3. Fallback: `claude-code` (preserve current behavior for ambiguous cases)

If detection resolves to anything other than `claude-code` → Mode Gate forces Mode A regardless of 5-criteria score.

User can still override with hard warning displayed.

## 5. File-level Changes (5 total)

### 5.1 `docs/claude/mode-selection-criteria.md`

Add new section after "## Hard Exclusions":

```markdown
## Reverse Hard Exclusion (Always Force Mode A)

Beyond the existing Hard Exclusions (which force Mode B), v5.6.0 adds the
reverse: certain conditions force Mode A regardless of 5-criteria score.

### Active harness detection

Mode B requires Claude Code's Task tool. On other harnesses, Mode B
partially fails. Detection order:

1. Read `.planning/config.json` field `active_harness`. If explicit (not `auto`),
   use that value.
2. If `auto`, check environment variables:
   - `$env:CLAUDECODE` set → `claude-code`
   - `$env:CURSOR_*` set → `cursor`
   - `$env:CODEX_*` or process `codex` → `codex`
   - `$env:OPENCODE_*` set → `opencode`
   - None match → fallback `claude-code` (preserves current behavior)
3. If detected harness != `claude-code`:
   - Force suggested mode = Mode A
   - Output reason: `"Mode B requires Claude Code Task tool. Detected harness: <name>. Forcing Mode A. Override with full understanding of partial-failure risk."`
4. User can override per existing rule (user-decision-wins). On override to
   Mode B with non-Claude harness, prepend warning:
   `"⚠ You are forcing Mode B on <harness>. Subagent dispatch and model
    selection may not work as designed. Proceed with manual review fallback ready."`

See `docs/claude/harness-compatibility.md` for full compatibility matrix.
```

## 6. Backward Compatibility

- Existing v5.5.x projects: `active_harness` field auto-added at next `/update-config` (or stays inferred via env detection if config field missing)
- Existing plans with `<model>opus</model>` etc.: unaffected (this is a Mode Gate change, not a Mode B internal change)
- Override path preserved: user can force Mode B on non-Claude harness with explicit warning acknowledged

## 7. Decisions Log

| # | Decision | Rationale |
|---|---|---|
| 1 | Strategy α (runtime) over β (per-market bundles) | 10x cheaper, single source of truth, eliminates drift class of bugs |
| 2 | Default `active_harness: auto` (env detect) | Lowest friction; works without user config change |
| 3 | Fallback to `claude-code` if detection ambiguous | Preserves current behavior; safest default |
| 4 | Allow user override Mode B on non-Claude with warning | Consistent with existing "user decision wins" principle |
| 5 | No Mode B internals refactor | Out of scope; would require multi-month effort for marginal benefit |

## 8. Testing

Manual eval scenarios:
- E1: On Claude Code, `active_harness: auto` → Mode Gate behaves as before (no force)
- E2: On Cursor (simulated env), `active_harness: auto` → Mode Gate forces A
- E3: User explicit `active_harness: codex` → Mode Gate forces A regardless of platform
- E4: User overrides Mode B on Cursor → warning shown, override accepted
- E5: Existing v5.5.x project (no `active_harness` field) → Mode Gate behaves same as v5.5.x (env detect path)

No automated tests (consistent with plugin self-dev convention from v5.4.0/v5.5.0).
