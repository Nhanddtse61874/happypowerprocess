# Process 2.0 — Memory Recall, Observability & Sandbox Verification (Design Spec)

**Date:** 2026-07-11
**Status:** DESIGN — STEP 5 output for `.planning/REQUIREMENTS.md` (Process 2.0 v1).
**Mode:** A (Solo). **Branch:** `feature/docs-consolidation-knowledge-layer-2026-07-08`.
**Requirements covered:** MEM-01..04, OBS-01/02, CFG-01, VER-01/02 (v1). MEM-05, EXE-01, OBS-03 are v2, out of scope here.

## 1. Design principles

1. **Absorb ideas, not runtimes.** Everything below is built from existing Claude Code primitives — markdown memory files, the `SessionStart` hook, the STEP 7 controller loop, the Bash tool. No external runtime, no new dependency (matches the v1 assumption in REQUIREMENTS.md).
2. **Hooks inform; the human-gated workflow acts.** Following the existing `hooks/session-start` precedent — a hook only *injects a reminder telling the agent to act*, it never acts itself. This keeps pillar #1 (never auto-advance) intact at the hook layer.
3. **Config-gated, default off.** Every capability is behind a `workflow.*` boolean, default `false` (CFG-01). Process 2.0 never adds overhead to a task that didn't opt in.
4. **The 3 pillars are structural, not just wording.** No auto-advance · REQ-ID traceability · AI does not self-declare done — enforced by design (below), not by prose.

## 2. Key design decisions (resolving the STEP 4 open questions)

### D1 — Two memory stores, with a hard boundary

| Store | Location | Scope | Cadence | Curated? |
|---|---|---|---|---|
| **Process memory** (Process 2.0) | `<project>/.claude/memory/` (committed to git) | process/workflow lessons: model escalations, plan misfires, config choices, workflow gotchas | auto-captured at STEP 11, human-reviewable | No (auto + English-normalized) |
| **Knowledge library** (existing) | `<project>/.claude/skills/<project>-*` | codebase facts: architecture, failure archaeology, config axes | STEP 11 Knowledge Sync | **Yes** (ground-truth, human-approved) |
| **Global/user memory** (native) | `~/.claude/projects/<slug>/memory/` | user prefs, feedback, cross-project | Claude Code native | n/a |

**Boundary rule (resolves risk #1 "one home per fact"):**
- Process memory captures **"how we worked"**; knowledge library captures **"what the code is."** Tie-break: a lesson about the *workflow/process* → process memory; a fact about the *codebase* → knowledge library.
- **Process memory MUST NOT write into `.claude/skills/<project>-*`** (auto vs curated is a doctrine clash — the knowledge library is ground-truth-only, human-gated).
- Both are **no-op when absent** (matches the existing conditional-hook convention).

**Why `<project>/.claude/memory/` (resolves risk #4 portability + write-fence):**
- Committed to git → portable across machines (`git clone` restores it; no re-init).
- Inside the write-fence (`.claude/` is already writable), and **NOT under `.planning/`** — so it is never silently un-committed by `commit_docs.planning_artifacts: false`.
- Format mirrors the native memory convention: a `MEMORY.md` index (one line per lesson) + one `.md` file per lesson, English-only.

### D2 — Memory scoping & recall (MEM-01/02/04)

- **Scope tag (MEM-02):** each lesson carries `scope: global | project`. Global lessons (user/feedback/reference-flavored) are few and stable; project lessons live in the project store. The always-loaded index stays small because project lessons are retrieved on demand, not preloaded.
- **Recall-on-demand (MEM-04):** STEP 0 recall does **not** load the whole `MEMORY.md`. It runs a Grep/Glob query over the memory store, ranks by (tag match + keyword overlap + recency), and loads only the top-K entries. Per-session context cost stays flat as the store grows.
- **Recall is an in-workflow agent step, not hook-only (resolves risk #2 + the mid-session-resume gap):** `SessionStart` does not fire on a mid-session STEP 0 Resume, so recall is a step the agent runs at STEP 0. The `SessionStart` hook may additionally inject a one-line reminder at startup (reusing the `<project-state-reminder>` pattern), but the agent step is the primary, reliable path.
- **v1 accepts lexical recall (grep).** Precision (not cost) is the limit; MEM-05 (semantic vector index @ threshold) is the v2 upgrade. MEM-03 keeps recall trustworthy in the meantime.

### D3 — Maintenance pass (MEM-03) — two entry points

A maintenance routine scans the process-memory store and **flags** duplicate / stale / superseded / contradictory entries for removal. It **flags, it does not auto-delete** (pillar #1) — the human approves deletions. Delivered as **both** (user decision 2026-07-11):
- **`/memory-clean` slash command** — on-demand, run whenever the user wants.
- **Inline STEP-11 sub-step** — a flag-and-report pass fires at Ship, surfacing candidates for the user to approve (never auto-deletes).

Reuses the existing memory guideline ("update an existing note rather than duplicate; delete notes that turn out to be wrong").

### D4 — Telemetry from the controller loop, not a hook (OBS-01/02)

- **Capture (OBS-01):** the STEP 7 controller loop (`subagent-driven-development`, at the existing per-task "update STATE.md" point) appends one line per task to `.planning/{phase}-telemetry.jsonl` — **append-only JSONL** (crash-tolerant; a partial line never corrupts prior data). Fields: `task_id`, `req_ids`, `model`, `tokens` (when available), `wall_clock`, `escalation` (e.g. `haiku→sonnet`), `result`.
- **Why the controller, not a hook (resolves risk #2):** token counts, per-subagent model, and escalation events are controller-side workflow state — a `PostToolUse`/`Stop` hook cannot see them reliably, and on Windows a missing Git Bash makes hook capture silently no-op (empty telemetry looks like a clean run). The controller already writes per-task state; telemetry rides that write.
- **Aggregate (OBS-02):** at STEP 11, `finishing-a-development-branch` reads the JSONL → renders a **Telemetry** table in `phase-SUMMARY.md` and adds a `telemetry` key to the `phase-summary-v1` output contract. Telemetry data in `.planning/` is ephemeral per-phase; the durable summary lives in the committed SUMMARY.

### D5 — Bounded, evidence-only sandbox verify (VER-01/02)

At STEP 8, when `workflow.sandbox_verify` is on and the task produced runnable code, an agent runs an `execute → observe → fix` loop, hard-constrained (resolves risk #3):
- **Iteration cap:** at most N fix iterations (default 3), then stop and report — never an unbounded loop.
- **Scope-fence:** each fix must trace to the task's REQ-ID and stay within the task's planned files (Surgical Changes). No touching files outside the plan.
- **No permission escalation:** uses the same Bash allowlist as the implementer; writes/destructive commands still hit the normal permission gate. The loop is never handed a blanket Bash/Write allowlist.
- **Evidence-only (VER-02):** the loop writes run evidence into the **`Evidence`** column of `phase-VERIFICATION.md`, in a section **separate** from the UAT approval. STEP 8a UAT (user tests, AI does not claim done) remains a distinct, unskippable human touchpoint. The `Decision` (PASS/PARTIAL/FAIL) stays human-driven. Verify **never** auto-passes STEP 8.

### D6 — English normalization (resolves risk #6)

Process-memory capture (STEP 11 write-back) normalizes lesson content to **English** before persisting, satisfying the plugin English-only source policy even when the session was conducted in another language.

### D7 — Config flags (CFG-01)

Three new booleans join the existing `workflow.*` group, default `false`, added to **both** `docs/claude/config-schema.md` (schema row + display-grouping) **and** `docs/claude/templates/config.json` (or the schema-drift hard-abort fires):

```jsonc
"workflow": {
  "research": true,
  "plan_check": true,
  "memory_recall":  false,   // MEM-01/02/03/04
  "telemetry":      false,   // OBS-01/02
  "sandbox_verify": false    // VER-01/02
}
```

## 4. Pillar preservation (audit)

| Pillar | How this design preserves it |
|---|---|
| Never auto-advance | Hooks only inject reminders; recall/telemetry are passive reads/writes; verify is bounded + evidence-only; every STEP gate unchanged; MEM-03 flags, never auto-deletes. |
| REQ-ID traceability | Every capability config-gated and REQ-mapped; verify fixes must trace to a REQ-ID; telemetry records `req_ids` per task. |
| AI does not self-declare done | Verify produces *evidence for* UAT, never a step-pass; STEP 8a UAT stays a distinct human touchpoint; `Decision` is human-driven. |
