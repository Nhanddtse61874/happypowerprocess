## What Was Built

### New skills

- **`/add-tech-stack`** ([skills/add-tech-stack/SKILL.md](../skills/add-tech-stack/SKILL.md)) — customize an existing plugin stack skill for the current project, or add a brand-new stack (Python, Go, Rust, etc.). Two flows: Scenario A (existing — keep/override/append/skip per section) and Scenario B (new — input/suggest/skip + variable section loop). Force both SKILL.md + AGENT.md when creating new; ask user file choice when editing existing. `--force` flag for power users. Plugin-path detection + cross-platform Glob fallback (re-uses v5.4.0 pattern). Pre-flow backup directories for rollback.

- **`/sync-stack-skill`** ([skills/sync-stack-skill/SKILL.md](../skills/sync-stack-skill/SKILL.md)) — three-way merge a customized snapshot with the latest plugin default. Per-section conflict detection with 4 patterns (both unchanged / plugin-only / user-only / both updated); manual-merge sub-flow with 3-pane view; apply-all-remaining shortcut for non-conflicts only. Supports `--all` for batch sync with summary. Plugin stack removal detection (auto-suggest convert source to `project`). Pre-sync `.pre-sync-backup` convention.

### Architecture detection (T1) integration

- **`skills/init-project/SKILL.md`** updated — adds new `## d2. Architecture Detection (T1 trigger)` section between sections d (Brownfield Handling) and e (Interactive Prompts). Heuristic detection (folder structure + 2-3 representative files) + opt-in web search. Confidence levels HIGH/MEDIUM/LOW. Edge cases for 0/conflicting/LOW confidence/web-fail handled. Greenfield path skips entirely. Section f File Creation also updated to copy `registry.json` template + create `.claude/stack-skills/` directory at init time.

### Stack registry + runtime lookup

- **`.claude/stack-skills/registry.json`** schema introduced — single source of truth for registered stacks per project. Tracks `source` state machine (`plugin` / `customized` / `project`), paths, sync history. Path-rewrite-on-flip rule: when `source` flips to `customized`, registry's `skill_path` and `agent_path` rewrite to `.claude/...` snapshot files (load-bearing for F2/F3 — see QA round 1 below).

- **`docs/claude/stack-skill-rule-map.md`** updated — new sections `## Runtime Lookup Order (v5.5.0+)` and `## Unknown Stack Behavior (T2)`. Registry path field is authoritative; project snapshots always win. T2 unknown stack mid-task halts with 2 options (interactive `/add-tech-stack` or cancel) — never auto-creates.

## Key Decisions

| # | Decision | Rationale |
|---|---|---|
| 1 | Section-level merge (not full-replace, not rule-level diff) | Stack skills are rich; full-replace loses default value, rule-level diff over-engineered. |
| 2 | Snapshot model (Hybrid C: snapshot + `/sync-stack-skill`) | Predictable mental model — user opens file and sees full effective rules. Drift handled by explicit re-sync, not runtime parser. |
| 3 | User rules win on conflict | User explicitly customizes for project-specific reason; default should never override deliberate customization. |
| 4 | E3 Conservative for architecture detection | Zero surprise; user fully controls scan/web/save decisions; reproducible. Trade-off: more prompts per init (~3/stack). |
| 5 | Web search always opt-in (no `--use-web` flag) | E3 spirit; force user to consent to token cost per use; flag would be hard to remember and undermine consent. |
| 6 | Template SKILL.md = 3 fixed top + Architecture + N variable + 2 fixed bottom | Matches structure of all 5 existing plugin skills; consistent ordering for AI normalization. |
| 7 | AGENT.md user inputs separately (not auto-derived from SKILL) | User-correctable identity prompts; AI still keeps content concise. AGENT.md does NOT auto-regenerate when SKILL changes. |
| 8 | Force both SKILL+AGENT on Scenario B; ask file choice on Scenario A | B is creation — both files needed. A is editing — user often only wants to tweak one. No `--skill-only` flag (poor UX). |
| 9 | Best-practice MINIMUM on explicit skip | User skip is an action, not silence. Slim minimum signals "intentionally light here" without empty section confusion. |
| 10 | Single registry.json (vs per-stack meta) | Adequate for v5.5.0 scale; per-stack meta files would fragment without proportional benefit. Possible v6.0 migration. |
| 11 | CLAUDE.md marker block + auto-regenerate | Pattern already used (`<!-- gitnexus:end -->`); inline table keeps AI context fresh; auto-regenerate keeps drift impossible. |
| 12 | Reserved names enforced (system names only — plugin defaults route to Scenario A) | Prevent ambiguity in registry semantics; allow legitimate edit of plugin defaults via Scenario A. |
| 13 | T2 unknown stack: halt + 2 options, no auto-create | E3 principle — AI never silently scaffolds. User must explicitly invoke `/add-tech-stack`. |
| 14 | Pre-flow backup directory + pre-sync `.pre-sync-backup` file | Two backup conventions for two failure shapes: customize abort vs sync abort. No auto-cleanup. |
| 15 | No file lock for concurrent editing | Single-user repo assumed; locks add code without solving the actual usage pattern. Document in skill instead. |
| 16 (QA round 1) | Path-rewrite-on-source-flip rule | C1 finding: registry must rewrite `skill_path` and `agent_path` when source flips to `customized`. Without this, runtime lookup loads plugin default and customization has no effect — load-bearing. |
| 17 (QA round 1) | Snapshot agent uses canonical long-form basename (Scenario A) | I1 finding: snapshot agent file must share canonical name with plugin agent (`implementer-dotnet-csharp.md`, not short `implementer-dotnet.md`) for true override semantics. |

## What Worked

- **11-step workflow ceremony** drove discipline again — same mature shape as v5.4.0. Each step had clear handoff and user touchpoint.
- **XML plans with frontmatter `must_haves`** (4 plans, 12 tasks) made Goal-Backward Verification mechanical — cross-reference truths/artifacts/key_links with files was systematic.
- **Subagent-driven execution** with model overrides per user: T4=sonnet, T5/T6=opus (the 2 large logic-heavy skills), T7=opus (init-project surgical edit), T11/T12=opus (rule-map runtime semantics). Sonnet sufficient for templates and command registrations.
- **Atomic commits** with REQ-ID + plan path in commit body — easy bisect, easy audit trail.
- **Surgical edits** verified via git diff stat for every modify task. T11 was 15 lines pure additions (zero deletions), T12 was 28 lines pure additions, T7 was 32 lines pure additions on init-project.
- **Cross-file consistency** maintained automatically via shared spec sections — marker text, file paths, skill names, command pattern all match across 20 changed files.
- **QA round 1 caught the load-bearing C1 bug** — the path-rewrite-on-flip rule was missing in initial implementation. Code-reviewer subagent traced from skill body → registry write → runtime lookup → spec §5.3 promise and identified the inconsistency. Fix took 1 batched commit (5 files, +58/-28).

## What Didn't Work / Lessons

- **Path semantics in distributed schema**: Initial implementation wrote snapshot files to `.claude/...` paths but the registry kept pointing to plugin paths. Three-way inconsistency between (a) registry path field, (b) snapshot file path on disk, (c) runtime lookup rule. The reviewer caught it because the spec §5.3 explicitly promised "project snapshot always wins if file exists" but the code didn't implement existence-check fallback nor path-rewrite. **Lesson**: when spec defines a runtime-time invariant (snapshot wins), the implementation must update the lookup-time data (registry path field) at the moment of customization (not later). State machine arrows in §5.4 should always include side-effects on related fields, not just the named field.

- **Naming asymmetry between plugin and snapshot**: Initial implementation wrote snapshot agent files to short-form names (`implementer-dotnet.md`) while plugin defaults use long-form (`implementer-dotnet-csharp.md`). Two files, two names, no override. **Lesson**: the override rule must preserve the canonical name. For Scenario A, derive snapshot basename from existing plugin `agent_path` basename (`implementer-dotnet-csharp`). For Scenario B (new stack), the snapshot name IS the canonical (no plugin to mirror).

- **PowerShell 5.1 `.Count` on single-item filter**: T1 implementer flagged this — `(arr | Where-Object {...}).Count` returns `$null` when filter matches exactly 1 item. All implementers worked around with `@(...)` wrapper. Plans 02-04 verify commands have the same issue. **Lesson**: Future plan templates should use `@()` wrapper consistently. Or migrate to PowerShell 7+ which collects to array automatically. Recorded as residual risk.

- **CHANGELOG format mismatch**: T10 plan template had `## v5.5.0 — Stack customization (2026-05-07)` heading style, but the existing CHANGELOG uses `## [5.5.0] - 2026-05-07` convention. Implementer correctly adapted to existing convention without prompting. **Lesson**: planner should always read existing CHANGELOG entries first when prescribing format — saves a round-trip clarification.

| R3 | PowerShell `.Count` pattern in plan files would fail on PS 5.1 fresh re-runs | Plans 02-04 not edited (out-of-scope for QA round 1 fix). Recorded; future plans use `@()` wrapper. |
| R4 | T2 detection heuristic (framework keywords + glob markers) may produce false negatives for unusual stacks | User can always invoke `/add-tech-stack` manually. Heuristic is best-effort. |
| R5 | Marker block manual edits between markers will be overwritten on next regenerate | Skill body warns + offers `preserve-manual` option per spec §8.7. |
| R6 | `--all` short-circuit on version match assumes byte-identical plugin content since last sync | Will miss issues if user manually edited snapshot. Not blocking for v5.5.0; document if it surfaces. |
